# Master Project Plan: Crypto, Simulation & Architecture

## 1. Cryptographic Upgrades (The "Missing" Layer)

### **A. Digital Signatures (ECDSA P-256)**

Currently, we use SHA-256 to _hash_ data (ensure content integrity). We are missing **Authenticity** (Who created it?).

- **Recommendation**: Implement **ECDSA (Elliptic Curve Digital Signature Algorithm) with P-256 curve**.
- **How it works**:
  1.  The "Commissioner" (Node) holds a **Private Key**.
  2.  Every time a block is created, the Node **SIGNS** the Block Hash with keys.
  3.  **Verification**: Anyone with the Public Key can verify the signature.
- **Why P-256?**: It's a standard NIST curve, widely used in government and HTTPS/TLS. It's faster and cleaner than RSA.

### **B. JSON vs. CSV**

You asked to swap JSON for CSV.

- **Analysis**:
  - **JSON (Current)**:
    - ✅ **Native**: JavaScript (Node) and PostgreSQL (`JSONB`) speak JSON natively.
    - ✅ **Nested**: Can store arrays (e.g., list of Tokens in a Sack) easily.
    - ✅ **Performance**: Extremely fast for web apps.
  - **CSV**:
    - ❌ **Flat**: Cannot handle nested data well (a sack with 10 tokens breaks the columns).
    - ❌ **Fragile**: Comma parsing issues if text contains commas.
    - ❌ **Slow**: Requires conversion to object for every read/write.
- **Verdict**: **Stay with JSON for the Database and Code.** Use CSV **only for external reports** (e.g., "Download Audit Log"). Using CSV for the core engine would make the system **slower and more error-prone**.

## 2. Deep-Dive: Hashing, Authenticity & Immutability (The "Root Level")

You asked for the **Exact Cryptographic Flow**. Here is the byte-level journey of data.

### **Phase 1: Input & Hashing (The "Fingerprint")**

**Event**: Farmer creates a Sack (ID: `TKN-123`).

1.  **Raw Data Extraction**:
    We take specific, critical fields. We do NOT hash the whole row (to avoid timestamp jitters).
    - `Payload = "TKN-123" + "Soham" + "50kg" + "Paddy"`
2.  **SHA-256 Hashing**:
    - We run `SHA256(Payload)`.
    - **Result**: `a591a6d40bf420404a011733cfb7b190d62c65bf0bcda32b57b277d9ad9f146e`
    - _Why?_: This string represents the **Content**. If someone changes "50kg" to "49kg", the hash becomes completely different (`b78...`).

### **Phase 2: Digital Signature (The "Author")**

**Event**: The Node (System) receives this Hash.

1.  **Signing**:
    - The Node uses its **Private Key (ECDSA P-256)** to sign the _Hash_.
    - `Sign("a591...", Private_Key) -> "Signature_XYZ"`
    - _Why?_: This proves **Authority**. Even if a hacker generates a valid hash for "49kg", they cannot generate a valid _Signature_ because they don't have the Private Key.

### **Phase 3: The Blockchain Link (Merkle & Chain)**

**Event**: Anchoring into the Ledger.

1.  **Previous Block Hash**: Typically `0000abc...` (Hash of Block N-1).
2.  **Block Construction**:
    - `Block_Data = Previous_Hash + Current_Data_Hash + Signature + Timestamp`
3.  **Final Block Hash**:
    - `SHA256(Block_Data) -> "0000def..."`
    - _Why?_: This links time. You cannot delete Block N-1 because Block N's hash _depends_ on it.

### **Phase 4: IPFS (The "Document")**

- **The "Same CID" Bug**: You noticed CIDs were identical. That was a mock placeholder.
- **The Fix**: A real CID is generated by hashing the _File Content_.
  - `IPFS_Hash(PDF_Content_File) -> QmXoypizjW3WknFiJnKL...`
- **Relationship**:
  - **Database**: Stores `QmXoy...` (The Pointer).
  - **IPFS Network**: Stores the actual PDF file.
  - **Verification**: If the File changes, the CID changes. If the CID changes, it mismatches the Ledger.

## 3. Handling Corrections & "Dead" Data

### **Q: How do we link changes (This was X, now it is Y)?**

**Answer**: By **Appending**, not Replacing.

- **Scenario**: Weight recorded as 60kg. Real weight is 50kg.
- **Wrong Way**: `UPDATE logs SET weight=50 WHERE id=...` (This breaks the hash).
- **Right Way (Blockchain)**:
  1.  Create **NEW Transaction**: `Correction Event`.
  2.  Payload: `{"original_ref": "Block_10", "new_value": 50, "reason": "Scale Error"}`.
  3.  **UI Logic**: The Dashboard reads _both_. It sees Block 10 (60kg) and Block 12 (Correction: 50kg). It displays: ~~60kg~~ **50kg**.
  - _Traceability_: You see _who_ made the mistake and _who_ fixed it.

### **Q: What about "Dead Ends" (Data stopping at MLS)?**

**Answer**: **Orphan Analysis**.

- We run an analytical query: `SELECT * FROM tokens WHERE current_phase != 'CONSUMER'`.
- **Report**: This generates a list of "Stuck Inventory".
- **Credibility**: Finding incomplete data is a _feature_, not a bug. It helps the government identify bottlenecks (e.g., "Why does PPC_Hyderabad have 500 stuck sacks?").

## 4. Answering Your Key Questions

### **Q1: How to show End-to-End?**

**Answer**: Use the **Two-Way Verification Modal** on a "Golden Record" (completed ID).

- Search `TKN-20260117-596D`.
- The Right-Side Timeline shows every step: Farmer -> PPC -> Miller -> Warehouse -> Shop.
- This visualizes the entire journey in one vertical flow.

### **Q2: How to stop change in Main DB?**

**Answer**: By design, Blockchain is **Append-Only**.

- **Database Level**: We revoke `UPDATE` and `DELETE` permissions on the `operational_logs` table for the application user. Only `INSERT` is allowed.
- **Crypto Level**: If someone forces a DB update (as root), the **Hashes will mismatch**. The "Verify" button would show "TAMPERED" because `Hash(New Data) != Stored Hash`.

### **Q3: How to start a New Chain? How is it stopped?**

**Answer**:

- **Start**: Truncating the DB (what we did earlier) effectively starts a new chain. The first new entry becomes "Block 1" (Genesis).
- **Stop**: You cannot "stop" a blockchain; you can only "pause" it by stopping the `sync_service` (the writer).

### **Q4: How can multiple people show?**

**Answer**: The system is **Web-Based**.

- We host the Frontend/Backend on a central server (or your laptop on a network).
- Users A, B, and C can all open `http://[YOUR-IP]:5173`.
- When You (User A) add data, **Socket.io broadcasts** the update. User B and User C see the new block appear **instantly** on their screens without refreshing.

### **Q5: How to show what is changed, and how will we tell them this is right?**

**Answer**:

- **Change Detection**: The `sync_service` compares the V8 Source vs. Ledger.
- **Verification**: If a user questions the data, you click the **"DB Admin"** button (PgAdmin). You show them the raw `data_payload` and the `hash`. You recalculate the hash live (using an online tool or script) to prove `SHA256(Payload) == Stored Hash`.
- **"IPFS + Blockchain Hash"**: This is the ultimate proof. The IPFS file is the "Document", the Blockchain Hash is the "Notary Stamp". If they match, it is undeniably "Right".
